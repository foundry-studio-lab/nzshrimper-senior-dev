# senior-dev v0.4 — friction pass

Date: 2026-09-30. Status: design agreed with the operator in session
(sections 1 and 2 approved), awaiting written-spec review.

## 1. Why

Evidence, not taste. An audit of all 441 archived sessions across the
operator's repos (July–September 2026, `*/.senior-dev/history/*.json`)
found the plugin's friction concentrated in five places:

| Friction | Evidence |
|---|---|
| Test loop: every fix re-ran the whole suite, each run surfaced a new failure, some tests contradicted each other | tsp_website 2026-09-08: one article took ~12 hours; the operator ordered "stop running tests", which then cost 8 separate bypasses |
| No way to change lane mid-run | 16 bypasses (`finish --force-open "escalating quick-fix to …"`), most of the 23 sessions closed with phases still `in_progress` |
| 3-cycle cap blocks recording the confirming approval | 11 bypasses ("cycle-3 nits fixed, approved at finish; the cap prevents recording") |
| Conductor names skills that do not exist | 27 degrades for the non-existent "built-in `verify`"; `/code-review` resolves to different skills on different machines (on this one, `~/.claude/skills/code-review` is Matt Pocock's two-axis review) |
| No clean close for "nothing needed doing" | ~6 bypasses ("no change needed", "superseded", "parked on sign-off") |

Reviews themselves earn their place (Codex NEEDS_REVISION 22% of 712
passes, Claude 18% of 665), so v0.4 removes friction around them, not them.

Research input for the review-naming and spec-axis items:
`docs/research/2026-09-30-mattpocock-skills-comparison.md`.

## 2. Goals and non-goals

Goals: break the test loop without ever letting a diff-caused failure ship;
turn the four other bypass patterns into first-class, logged operations.

Non-goals (ledgered for later): red-loop gate on `debug`; a `retro` step;
a `matt` skill source; Claude review on Codex hosts; a Codex hang/timeout
rule; plugin-level parsing of test output other than JUnit XML.

Compatibility: a repo with no `tests` config keeps today's behaviour
exactly (`tests-green` timestamp, no full-run requirement). Sessions
started before 0.4 keep working; new state fields are optional on read.

## 3. The test runner

### 3.1 Per-repo test config

`skills.json` gains an optional `tests` block:

```json
"tests": {
  "full":    "npm test -- --reporter=junit --outputFile=.senior-dev/junit.xml",
  "related": "npx vitest related --run {files}",
  "one":     "npx vitest run {test} --reporter=junit --outputFile=.senior-dev/junit.xml",
  "report":  ".senior-dev/junit.xml",
  "setup":   "ln -s \"$SENIOR_DEV_MAIN/node_modules\" node_modules",
  "build":   "npm run build"
}
```

- `full` required; `related`, `one`, `report`, `setup`, `build` optional.
- `{files}` / `{test}` are substituted with each value single-quote escaped
  for the shell; `one` may also use `{file}` and `{name}`, the two halves
  of a test id (`classname > name`, split at the first ` > `). The
  templates themselves are operator-written config.
- Tests run in the checkout the CLI is invoked from (a worktree during a
  feature lane), not the main checkout that holds state; `SENIOR_DEV_MAIN`
  is that checkout's root.
- `report` is a JUnit XML path relative to the directory the command ran
  in. It is REQUIRED for the pre-existing proof (§3.4) and so for any
  waiver of a failing full run (§3.6); scoped runs work without it.
- `setup` runs inside the proof worktree before its test, with
  `SENIOR_DEV_MAIN=<main checkout root>` in the environment.
- Written with `state-cli skills-config set-tests --full "<cmd>" [--related
  …] [--one …] [--report …] [--setup …] [--build …]`; `skills-config set`
  preserves the block. `stampVersion`: `tests` present → version 4, else
  models present → 3, else 2. `readSkillsConfig` accepts 1–4 and validates
  `tests` (plain object, string values, `full` non-empty).
- The conductor asks for the commands once per repo, the first time a lane
  with an `implement` phase starts, offering a guess from `package.json`
  (or the repo's CLAUDE.md). The operator may decline: recorded as
  `tests: {"none": true}`, and the repo stays on `tests-green`.

### 3.2 `state-cli test`

One runner, every mode records a run:

| Mode | Runs | Notes |
|---|---|---|
| `--affected [files…]` | `related` with `{files}` | Files default to those changed since the last full run's commit (or the session's `baseHead`) plus uncommitted changes. No `related` configured → falls back to `full`. No changed files → recorded green with `files: []`, nothing run. |
| `--one <test>` | `one` with `{test}` | Appends to that test's pass/fail history (§3.5). |
| `--full` | `full` | Parses `report` when configured to list failing test ids. |
| `--build` | `build` | Required by `ship` only if configured. |
| `--preexisting <test>` | see §3.4 | |

Each run is appended to `state.testRuns[]`:

```json
{ "id": 7, "kind": "affected|one|full|build|preexisting", "cmd": "<resolved>",
  "files": [], "test": null, "exit": 0, "failures": ["<id>", …],
  "head": "<commit sha>", "tree": "<tree sha>",
  "phase": "implement", "sinceFull": 5, "at": "<iso>" }
```

- `tree` is the tree the working state WOULD commit as: a temporary index
  (`GIT_INDEX_FILE=<tmp> git add -A && git write-tree`), so tracked edits
  and untracked non-ignored files are included and `.senior-dev/` (already
  in `.git/info/exclude`) is not. A run made before committing therefore
  matches `HEAD^{tree}` after the commit, with no rerun. The real index is
  never touched.
- A zero exit also stamps `testsGreenAt` on the current phase, so the
  existing commit gate is unchanged. A non-zero exit never does.
- Output streams through to the terminal; the CLI exits with the test
  command's exit code after recording, so a caller sees red as red.
- Failure ids come from JUnit `<testcase classname name>` elements that
  contain `<failure>` or `<error>`, as `classname > name`. A missing or
  unparseable report records `failures: null` (unknown), never `[]`.

### 3.3 Integration gate (repos with a `tests` config)

`integrationBlockers(state, { tests, trees })` — the caller passes the
trees the action ships (or none). Blocks unless:

1. there is a full run F (the latest one), and
2. F is green, OR F's `failures` is a non-null list whose every id has a
   `preexisting` proof (§3.4) AND `ship` is armed (§3.6), and
3. for every shipped tree: F.tree equals it, OR there is a later green
   affected run A with `A.sinceFull == F.id` and `A.tree` equal to it.

Rules 1–2 apply to every integration action. Rule 3 applies only where
code ships: `git push` and `gh pr create`, not `git merge` or
pre-merge-commit (the merge tree does not exist yet); `trees` absent skips
it, and a null entry or an empty list is never covered. The Claude Code
gate checks `HEAD^{tree}` of the target checkout (the git segment's `-C`
path resolved against the payload cwd, else the cwd); the guard's
pre-push checks `<local sha>^{tree}` of every non-delete ref on its stdin,
and does so even when a pass token is present unless the token records a
consumed bypass (`bypassed: true`). A run recorded before committing
matches because of §3.2's would-commit tree.

Rule 3 is the loop-breaker: after one full run, later commits cost only
their related tests. Nothing in senior-dev ever demands a second full run.
Comparing trees, not commits, lets a no-ff merge commit with an identical
tree pass without rerunning.

The conductor's test policy (SKILL.md) matches: after a fix, `test
--affected`; `test --full` once, when implement is complete (in the
background when it can outlast the Bash timeout); never re-run the full
suite to "check" a fix.

### 3.4 Proving a failure pre-existed: `test --preexisting <test>`

1. Requires `one` and `report` configured, and a known base: the session's
   `baseHead` (recorded at `init`, §4), falling back to `git merge-base
   HEAD <default branch>` for sessions started before 0.4.
2. `git worktree add --detach <tmp> <base>` in the OS temp dir; run
   `setup` there if configured; run `one` for the test there; parse the
   report.
3. Run `one` for the test on HEAD; parse the report.
4. Records `preexisting` with `proven: true` only if the test id appears
   as FAILED in BOTH reports. A test absent from the base report (the
   runner crashed, deps missing, test did not exist) is `proven: false`
   with the reason — a crash must never read as a pre-existing failure.
   Fails on HEAD only → `proven: false`, "caused by this change".
5. The temp worktree is removed (`git worktree remove --force`) in a
   `finally`, and `git worktree prune` runs; a leftover is reported.

### 3.5 Contradiction stop

For every run whose report parsed (`--one`, and `--affected`/`--full`
when `report` is configured), per test id, the CLI keeps the sequence of
pass/fail outcomes in the current phase. When a test's sequence contains fail → pass → fail, the
run prints `CONTRADICTION: <test> has failed, passed, and failed again this
phase` and records `state.contradictions[]` `{test, phase, at}`. While an
unresolved contradiction exists, `test --one` / `--affected` still run but
print the stop line again; the conductor must stop fixing, show the
operator both tests involved, and ask which behaviour is right. The
operator's answer is recorded with `state-cli test --resolve <test>
--reason "<answer>"`.

### 3.6 Ship override: `/senior-dev:ship <reason>`

Operator-only, like bypass (command file, reason read verbatim from
stdin). `state-cli ship --reason-stdin` checks, at arming time:

- nothing at the current tree is caused by the diff: either the latest
  full run F is at the current tree, or a green affected run with
  `sinceFull == F.id` is;
- F exists and its `failures` is a non-null list with every id proven
  pre-existing (§3.4) (a green F needs no ship at all; `ship` says so);
- a `build` run at the current tree is green, when `build` is configured.

Any unmet condition → refused, naming each failing test caused by the diff
or each missing run. On success, `state.ship = {reason, at, fullRun: F.id}`
is set for the rest of the session and appears in `status` and the
archive. It waives ONLY the pre-existing test failures (§3.3 rule 2).
Reviews, verify, and the docs gate still apply. A later commit re-checks
§3.3 rule 3 as usual, so new code after `ship` still needs its affected
tests green. The conductor, once `ship` is armed, stops chasing
pre-existing failures.

## 4. Reclassify: `state-cli reclassify --type <new> --reason "<why>" [--by-operator]`

- Same session, same task. `chain` becomes the new lane's chain; phase
  records are all kept (a phase not in the new chain stays in `phases`
  but no longer gates); `docsGate` gains the new lane's items (false)
  while keeping any already true; reviews, runs, dispatches kept.
- Rank: investigation 0, docs-only 1, quick-fix 2, bug-fix 3, refactor 3,
  feature 4. Same or higher rank: allowed. Lower rank: refused without
  `--by-operator` (the operator's yes).
- Appends `state.reclassifications[] {from, to, reason, byOperator, at}`;
  no bypass entry. `status` shows the history.
- `init` now also records `baseHead` (HEAD sha) and `baseRefs` (every
  `refs/heads/*` sha) for §3.4 and §6.
- Conductor escalation rule rewritten to use `reclassify`.

## 5. Review cap and skill names

### 5.1 Cycle 4 records confirmations only

`review` accepts cycle 4 only with `--verdict APPROVED` (the pass that
confirms the cycle-3 fixes); cycle 4 NEEDS_REVISION and any cycle ≥ 5
keep the refusal "cycle cap is 3 - stop iterating and escalate to the
operator". Adjudication on cycle 4 is not needed (it can only approve).

### 5.2 Name only skills that exist

- `verify` phase: `superpowers:verification-before-completion` is the
  skill. The "built-in `verify`" wording and its degrade instruction go.
- Claude review pass: `superpowers:requesting-code-review`. `/code-review`
  is used only when a skill of that exact name is in the session's skill
  list, and the conductor records which skill ran (`dispatch`/review
  note). Same for the §5 finish pass.
- Engage (after `init`): check every resolved phase skill against the
  session's visible skill list once, and record any degrade then.
- `description:` frontmatter of the conductor updated to match.

### 5.3 Spec axis in review

Both the Claude review brief and `references/codex-review-prompt.md` gain:
"For lanes with a committed spec, compare the diff to it and report
missing requirements, scope beyond it, and behaviour that contradicts it
as concerns." The Codex prompt gets a `<SPEC>` placeholder (path, or
`none`).

## 6. No-change close: `state-cli finish --no-change "<reason>"`

Allowed only when the CLI verifies all of: HEAD == `baseHead`; every
`refs/heads/*` sha equals its `baseRefs` value (a new branch still at
`baseHead` is fine); `git status --porcelain` is empty; `git worktree
list` shows only the main checkout. Otherwise refused with what changed.
Records `outcome: "no-change"` and the reason; no bypass entry; open gate
items are not demanded. Sessions without `baseHead` (pre-0.4) are refused
with "use finish or finish --force-open".

## 8. Testing

Unit tests with temp git repos (mkdtemp, as the existing suites do) and
tiny fake test commands (`node -e` scripts that exit 0/1 and write a
JUnit file), covering: v4 config round-trip and preservation; affected
file defaulting; tree-based coverage rule incl. a pre-commit run matching the committed
tree and the real index left untouched;
JUnit parse incl. missing report → `null`; pre-existing proof for
fails-both / fails-HEAD-only / base-crash (absent from report) / worktree
cleanup on throw; contradiction detection and resolve; ship refusals for
each unmet condition and success; ship does not waive reviews or docs;
reclassify up, lateral, down refused, down with operator; cycle 4
APPROVED accepted, NEEDS_REVISION refused, cycle 5 refused; no-change
finish accepted and each refusal; a repo without `tests` config behaves
exactly as 0.3.1. Live smoke items added to SMOKE.md for the ship path
and a real vitest repo.

## 9. Ceilings (known, accepted)

- Pre-existing proof and ship waivers need a JUnit report. Runners that
  cannot emit one get scoped reruns and the one-full-run rule, but a red
  full run on such a repo cannot be waived.
- `related` quality is the runner's (vitest/jest module graph). A test
  outside the graph that the change breaks is caught only by the one full
  run — which is why that run stays mandatory.
- Everything still trusts the operator's configured commands.
- `gh pr merge` gets rules 1–2 only: the server-side merge tree is never
  tested locally.
- Without the guard installed, `cd X && git push` and an explicit refspec
  naming a branch other than the target checkout's HEAD are checked
  against the target checkout's HEAD only.
- A test that fails on the base commit for an ENVIRONMENTAL reason (gitignored fixtures / .env absent from the proof worktree, a runtime-only dependency with no `setup`) reads as PROVEN when HEAD also fails.
- Without the guard, `git merge … && git push` in one command is checked against the pre-merge HEAD.
- `git -C <repo> push` run from a directory outside any repo finds no session (the guard catches it).
- A session-wide `ship` also waives a LATER full run whose failures are all proven (`ship.fullRun` then names the earlier run).
- An annotated tag created at `baseHead` is refused by `finish --no-change` (lightweight tags pass).
